# A 股 ETF 日 K 线统计分析系统产品需求文档（PRD）

**文档版本：** V1.0  
**产品类型：** Next.js Web 数据分析系统  
**主要用户：** 个人量化研究者  
**开发方式：** Codex 分阶段实现  
**核心目标：** 对已有 ETF 日 K 线进行全面统计分析，并将指标、特征及统计结果提前计算、持久化，为后续量化回测提供数据基础。

---

## 1. 产品概述

### 1.1 产品背景

当前系统已经具备 ETF 日 K 线爬虫及行情数据存储能力。下一阶段不再开发爬虫，而是围绕已存储的历史行情，建设统一的统计分析系统。

系统需要对每只 ETF 从现有历史数据起点至最新日期的行情进行计算，提取价格特征、技术指标、收益分布、风险指标、K 线形态、量价关系、趋势状态等信息。

系统不仅用于查看行情，更用于回答以下问题：

- 一只 ETF 的收益、风险和波动特征是什么？
- 不同 ETF 的走势、收益及风险有什么区别？
- 某种 K 线形态或技术指标出现后，后续收益的分布是什么？
- ETF 在什么情况下容易出现趋势延续、反转或大幅回撤？
- 哪些统计规律值得进一步设计成量化策略并进行回测？

### 1.2 产品目标

1. 对现有 ETF 日 K 线进行系统化、可复现的统计分析。
2. 将技术指标、日度特征、滚动统计及历史分析结果预先计算并保存到数据库。
3. 支持首次全量计算，以及行情更新后的增量计算和历史修正重算。
4. 通过 Web 界面查询、筛选、比较和可视化分析结果。
5. 为后续量化回测系统提供统一的数据和指标基础。

### 1.3 本期不包含的功能

- ETF 行情爬虫及行情采集管理系统的重新开发。
- 实盘交易、自动下单、券商连接。
- 量化策略编辑器及完整回测引擎。
- 机器学习预测、AI 自动交易信号。
- 分钟级、逐笔级及盘口数据分析。

本期可以为后续回测保留数据接口，但不实现完整回测功能。

## 2. 已有数据与系统约束

### 2.1 现有 K 线模型

当前已有 Prisma 模型：

```prisma
model Kline {
  code          String
  date          Int
  open          Float
  high          Float
  low           Float
  close         Float
  volume        Float
  amount        Float
  change        Float
  changePercent Float

  @@id([code, date])
  @@unique([code, date])
  @@index([code, date])
  @@map("kline")
}
```

以上模型是本项目现有基础，开发前必须检查实际 Prisma Schema 和数据库，确认字段、数据库类型及行情口径，不得直接假设示例就是完整定义。

实施要求：

- 复用现有 `Kline` 数据，不重复建立一套行情数据。
- 不修改爬虫的既有职责。
- 不得未经确认清空、重建或批量覆盖现有行情数据。
- 可以在不破坏兼容性的前提下调整冗余索引或约束，但应提供迁移方案。
- `date` 统一按 `YYYYMMDD` 整数理解，实际数据必须在开发前验证。
- 必须确认 `change` 和 `changePercent` 的定义及其价格口径，不得默认它们等于相邻前复权收盘价的收益率。

### 2.2 价格口径

本系统统一使用前复权 K 线进行技术指标和历史价格路径研究。

基本规则：

1. 技术指标使用统一的前复权 OHLC 价格计算。
2. N 日收益率统一使用前复权收盘价计算。
3. 价格涨跌幅、振幅、均线、波动率等指标必须使用文档规定的统一公式。
4. 成交量和成交额使用原始行情中的对应字段；不得对其进行未经定义的价格复权处理。
5. 如果数据源会回溯调整前复权历史价格，需要支持识别历史行情变更并触发重算。
6. 前复权价格用于历史研究，不代表历史真实成交价格。后续回测必须独立定义成交价格与收益核算规则。

## 3. 核心产品原则

### 3.1 预计算优先

**所有需要遍历历史 K 线的指标和统计分析，都必须由后台任务预先计算并持久化。**

页面请求和普通查询 API 不得临时执行全历史指标计算、全量统计或完整事件研究。

允许在请求时执行的操作：

- 按 ETF、日期、指标类型筛选结果。
- 分页读取预计算结果。
- 查询任务状态和计算版本。
- 对已持久化数据进行轻量查询、排序和展示。
- 对小规模结果进行必要的展示层处理。

禁止在请求时执行的操作：

- 临时遍历全部历史 K 线计算 RSI、MACD 等指标。
- 每次打开 ETF 页面都重新计算完整历史收益分布。
- 每次查询事件研究都重新扫描全部行情。
- 在前端执行全历史指标计算来替代后台计算。

### 3.2 计算结果可追溯

每类预计算结果必须能够追溯：

- 使用的行情数据范围。
- 数据版本或数据修订版本。
- 计算算法版本。
- 计算参数。
- 计算时间及任务状态。
- 统计样本数量和有效性。

### 3.3 全量与增量一致

相同的行情数据版本、计算算法版本和参数下，全量计算与增量计算必须得到一致的结果，允许范围内的浮点数误差除外。

## 5. ETF 分析总览

### 5.1 功能目标

提供所有 ETF 的分析入口，帮助用户快速发现值得进一步研究的标的。

### 5.2 页面功能

支持：

- 查看系统内 ETF 数量及数据覆盖情况。
- 按 ETF 代码、名称（如果已有名称数据）、数据起止日期搜索。
- 按收益、波动率、最大回撤等已计算指标排序。
- 筛选计算状态正常、待计算、计算失败或结果过期的 ETF。
- 进入单只 ETF 的详细分析页面。
- 查看最新计算时间及数据版本。

### 5.3 展示字段

每只 ETF 可展示：

- ETF 代码。
- 历史数据起止日期。
- K 线数量。
- 最新交易日。
- 累计收益率。
- 年化收益率。
- 年化波动率。
- 最大回撤。
- Sharpe 比率。
- 最新趋势状态。
- 计算结果状态。

没有足够数据的指标显示为空值和原因，不允许默认填充为零。

## 6. 数据质量分析

### 6.1 检查项目

对每只 ETF 的历史行情执行以下检查：

- 日期是否重复。
- OHLC 是否存在非正数。
- 最高价是否不低于开盘价、收盘价和最低价。
- 最低价是否不高于开盘价、收盘价和最高价。
- 成交量、成交额是否出现负数。
- 是否存在空值、非有限数值。
- 是否存在异常价格跳变。
- 日期序列是否存在异常间隔。
- 数据是否有明显的前后不一致。
- `change`、`changePercent` 与收盘价变化是否符合数据源定义。

交易日缺失检查必须考虑实际交易日历。周末、法定节假日和正常休市不应被错误标记为缺失交易日。

### 6.2 异常分类

- 错误数据：违反基本价格约束。
- 可疑数据：异常跳变或字段关系不一致。
- 疑似缺失：预期交易日缺少行情。
- 口径不一致：价格或涨跌幅字段不符合约定口径。

### 6.3 处理原则

数据质量模块默认只检查、记录和展示问题，不自动修改原始 K 线。

用户应能够查看异常日期、异常类型、涉及字段和检查规则。

数据质量检查结果必须持久化，行情更新或历史修正后重新检查受影响的数据范围。

## 7. 日度特征与技术指标

### 7.1 日度基础特征

每个交易日预计算：

- 当日涨跌幅。
- 开盘至收盘收益率。
- 收盘至次日收盘收益率（仅作为事后收益标签，不可用于当日信号）。
- 当日振幅。
- K 线实体大小。
- 上影线长度。
- 下影线长度。
- 实体占振幅比例。
- 收盘价在当日高低区间中的位置。
- 成交量变化率。
- 成交额变化率。
- 相对历史均量。
- 是否创新高或创新低。
- 连续上涨或连续下跌天数。
- 距离历史高点的回撤幅度。

所有比率和特征必须定义分母为零、缺失值和异常值的处理方式。

### 7.2 技术指标

第一期支持：

| 类别     | 指标                  |
| -------- | --------------------- |
| 均线     | SMA、EMA              |
| 趋势     | MACD、ADX、DMI        |
| 动量     | RSI、ROC、Momentum    |
| 波动率   | ATR、布林带           |
| 区间突破 | Donchian Channel      |
| 超买超卖 | KDJ、CCI、Williams %R |
| 量价     | OBV、MFI              |

默认参数建议如下，均需允许在计算配置中调整：

- SMA：5、10、20、30、60、120、250。
- EMA：12、26、50、200。
- MACD：12、26、9。
- RSI：6、14、24。
- 布林带：20 日均线、2 倍标准差。
- ATR：14。
- ADX/DMI：14。
- KDJ：9、3、3。
- CCI：20。
- Williams %R：14。
- Donchian Channel：20、55。

指标公式、初始化方法、标准差计算方式、平滑算法和预热期必须在计算规范中固定，不能仅根据名称自行选择实现。

### 7.3 指标结果要求

每个 ETF 每个交易日的指标结果应当能够查询。

对于尚未达到预热期的日期，保存空值或明确的不可用状态，不得使用零值伪造指标。

指标参数发生变化时，必须识别为新的计算版本，并重新生成对应结果。

## 8. 收益与风险统计

支持单只 ETF 的全历史和指定区间统计。

### 8.1 收益分析

预计算以下周期的收益率：

- 1、2、3、5、10、20、60、120、250 个交易日。

每个周期统计：

- 有效样本数。
- 均值。
- 中位数。
- 标准差。
- 最小值与最大值。
- 正收益比例。
- 负收益比例。
- 主要分位数，例如 P5、P25、P75、P95。
- 偏度与峰度。

### 8.2 风险分析

支持：

- 累计收益率。
- 年化收益率。
- 年化波动率。
- 下行波动率。
- 最大回撤。
- 最大回撤持续时间。
- 回撤恢复时间。
- 历史 VaR。
- 历史 CVaR。
- Sharpe 比率。
- Sortino 比率。
- Calmar 比率。
- Gain-to-Pain 比率。

默认无风险利率为零，后续可以配置。若修改无风险利率，必须重新计算相关风险调整指标。

年化交易日数默认采用 252。年化收益率、波动率、最大回撤和风险比率的公式必须统一，且在页面提供简要定义。

最大回撤需要区分：

1. 指定统计区间内的最大回撤。
2. 从历史起点开始计算的累计历史最大回撤。

不得将两者混为一谈。

### 8.3 收益分布展示

支持收益率直方图、分位数图、滚动收益曲线、回撤曲线和收益风险比较。

图表直接使用已存储的统计结果，不在浏览器中重新计算全部历史指标。

---

## 9. 趋势与波动率分析

### 9.1 趋势状态

根据已计算的指标，为每个交易日生成趋势分类：

- 上涨趋势。
- 下跌趋势。
- 震荡状态。
- 状态不明确。

趋势分类规则必须明确，例如均线关系、均线斜率和趋势强度的组合条件。具体阈值必须配置化，不能由不同页面分别定义。

### 9.2 波动率分析

支持：

- 滚动收益波动率。
- ATR 及其相对价格的比例。
- 布林带宽度。
- 波动率分位数。
- 波动率扩张与收缩状态。
- 波动率聚集分析。

支持按时间查看趋势状态与波动率状态的历史变化，并统计各状态的持续时间、发生频率和对应收益分布。

---

## 10. K 线形态分析

第一期支持识别以下形态：

- 阳线、阴线、十字线。
- 长上影线、长下影线。
- 大实体 K 线。
- 吞没形态。
- 孕线形态。
- 跳空（仅依据日 K 数据定义可观察的价格缺口）。
- 突破近期高点或低点。
- 冲高回落。
- 低开高走。
- 放量上涨、放量下跌。

每种形态必须明确计算条件和参数。

支持按 ETF、时间区间、形态类型查询历史发生日期，并统计形态出现后的 1、3、5、10、20、60 个交易日收益。

形态识别条件只能使用当日及此前已知的数据，不允许引用未来行情来决定当日形态。

---

## 11. 量价关系分析

分析成交量、成交额和价格变化之间的关系。

包括：

- 成交量和成交额分布。
- 相对均量。
- 放量上涨与放量下跌。
- 缩量上涨与缩量下跌。
- 价格创新高但成交量未同步增长。
- 价格下跌但成交量未同步增长。
- 成交量突增与后续收益。
- 成交额与收益波动的关系。
- Amihud 非流动性代理指标（在字段有效时）。

量价分类阈值必须可配置。应说明成交量、成交额可能受到 ETF 份额变化、市场流动性和数据源口径影响，不能直接将相关性解释为因果关系。

---

## 12. 连续涨跌、回撤与反弹

支持以下统计：

- 连续上涨天数分布。
- 连续下跌天数分布。
- 连续上涨或下跌后未来收益分布。
- 距离历史高点的回撤幅度。
- 回撤持续时间。
- 从局部低点反弹的幅度。
- 从高点下跌达到指定阈值的发生次数。
- 创历史新高后的未来收益。
- 创阶段新低后的未来收益。
- 回撤达到指定阈值后的恢复情况。

支持自定义阈值，例如回撤 5%、10%、15%、20%。

历史波段高低点应区分事后识别结果与当时可确认的信息。任何使用未来 K 线确认的波段标记，都必须标明其属于事后分析，不得直接作为当时可交易信号。

---

## 13. 时间周期与自相关分析

### 13.1 时间统计

支持：

- 年度收益统计。
- 季度收益统计。
- 月度收益统计。
- 星期收益统计。
- 月初、月中、月末统计。
- 不同年份的波动率及最大回撤比较。
- 不同市场状态下的收益分布。

必须说明每类统计的样本定义，避免将不同周期的收益重复计算后误认为独立样本。

### 13.2 自相关与动量反转

支持计算：

- 日收益率自相关。
- 多阶收益率自相关。
- 不同窗口的动量表现。
- 不同窗口的反转表现。
- 不同波动率状态下的动量与反转表现。

统计结果必须显示样本数，并避免仅凭相关性推断稳定盈利能力。

---

## 14. 事件研究

### 14.1 功能目标

事件研究是本系统的重要模块，用于研究某种条件发生后，后续收益的历史分布。

### 14.2 支持的事件类型

第一期支持：

- 均线金叉和死叉。
- 收盘价突破布林上轨或下轨。
- 布林带宽度达到指定低分位或高分位。
- RSI 上穿或下穿指定阈值。
- MACD 金叉或死叉。
- 成交量显著放大。
- 连续上涨或连续下跌达到指定天数。
- 创近期新高或新低。
- ATR 突增。
- 最大回撤达到指定阈值。
- 用户定义的简单指标组合条件。

### 14.3 事件研究结果

针对每个事件类型和参数，统计：

- 事件发生次数。
- 有效样本数。
- 事件发生日期。
- 后续 1、3、5、10、20、60 个交易日收益。
- 后续收益均值和中位数。
- 正收益比例。
- 收益分位数。
- 最大有利变动和最大不利变动（需明确观察窗口和计算公式）。
- 同期无条件收益基准。
- 相对基准的收益差。
- 适当的置信区间。

事件发生后尚未走完观察期的样本，应标记为未成熟，不得作为完整样本参与对应周期的最终统计。

### 14.4 事件去重

对于连续多日满足同一条件的事件，必须定义处理方式：

- 每日均记为事件；或
- 仅记录条件从不满足变为满足的首次触发。

默认采用首次触发，具体事件允许配置。

### 14.5 防止未来数据泄漏

事件在日期 T 发生时，其条件只能使用截至 T 日可用的数据。

未来收益标签只用于事后统计，不得反向影响 T 日的事件判断。

行情历史修正后，应重新计算受影响的事件日期及未来收益标签。

## 15. ETF 横向比较

支持选择多只 ETF 进行对比。

比较维度：

- 累计收益率。
- 年化收益率。
- 年化波动率。
- 最大回撤。
- Sharpe、Sortino、Calmar 比率。
- 不同周期收益率。
- 收益分布。
- 趋势状态分布。
- 波动率分布。
- 指定事件的发生频率和后续收益。

支持收益曲线、风险收益散点图、指标对比表和收益相关矩阵。

比较时必须统一统计区间和收益计算口径。对于历史起点不同的 ETF，应明确共同区间或各自完整区间，不能直接将不可比的累计收益混合排名。

## 16. 预计算与任务管理

### 16.1 计算触发

现有行情写入后，系统应能够获知哪些 ETF、哪些日期发生新增或修改，并生成相应的后台计算任务。

如果爬虫暂时无法直接调用新模块，可先提供独立的计算任务入口或定时检查机制；不得要求重写爬虫。

### 16.2 计算任务类型

- 首次全量初始化。
- 单只 ETF 全量重算。
- 新增 K 线增量计算。
- 历史行情修正重算。
- 指标参数变更重算。
- 历史统计刷新。
- 事件研究刷新。
- 数据质量检查。

### 16.3 计算依赖

计算顺序必须明确：

1. 验证行情数据。
2. 计算日度基础特征。
3. 计算技术指标。
4. 计算滚动统计与趋势状态。
5. 计算历史统计汇总。
6. 计算事件与未来收益标签。
7. 校验结果并发布。

### 16.4 增量计算要求

- 新增行情时，只计算受影响的结果范围。
- 滚动指标根据窗口依赖确定重算范围。
- EMA、MACD 等递归指标遇到历史修正时，原则上从修正日期重新计算至末尾。
- 前复权历史值发生回溯变化时，应根据数据源提供的变更范围确定重算范围；无法可靠识别时，允许对受影响 ETF 全量重算。
- 事件研究必须处理事件新增、撤销和未来收益标签成熟。
- 对无法可靠增量更新的全历史统计，采用分区重算或全量重算，并明确触发条件。

### 16.5 任务可靠性

任务系统必须支持：

- 待执行、执行中、成功、失败、取消等状态。
- 失败原因和重试次数。
- 可重试任务。
- 同一计算任务的幂等处理。
- 同一 ETF 相关任务的必要并发控制。
- 过期结果识别。
- 历史重算。
- 任务执行时间和计算范围查询。

任务成功不能仅表示程序没有报错，还必须确认结果已写入并通过必要校验。

### 16.6 结果发布

对于涉及多张结果表的计算，应避免前端读到部分更新的结果。

优先使用计算批次或版本化结果：先写入待发布结果，完成校验后再切换到当前有效版本。

如果计算失败，应保留上一份完整结果，并明确显示其已经过期或计算失败，不能将旧结果伪装成最新结果。

## 17. 数据库设计要求

开发前先检查现有数据库和 Prisma Schema，再决定具体字段和迁移方案。

逻辑上建议包含以下数据：

### 17.1 `Kline`

现有行情表，作为计算输入，不重复存储相同的行情。

### 17.2 `KlineFeature`

按 ETF 和交易日保存日度特征与技术指标。

要求：

- 每个 ETF、每个日期具有唯一标识。
- 常用指标使用明确字段。
- 缺失值使用可空字段或明确状态。
- 支持按 ETF 和日期范围高效查询。
- 记录计算版本或所属计算批次。

### 17.3 `KlineStatistic`

保存滚动收益、波动率、回撤、趋势状态等日度统计。

如果与 `KlineFeature` 的字段边界难以清晰划分，可以合并存储；不得为了形式而制造过度复杂的表结构。

### 17.4 `AnalysisSnapshot`

保存 ETF 级别、区间级别的统计汇总，例如收益分布、风险指标、时间周期统计。

### 17.5 `EventStudyResult`

保存事件定义、事件日期、未来收益标签和统计结果。可以将事件定义与事件结果分开设计，以便复用和重算。

### 17.6 `AnalysisJob`

保存后台任务状态、任务类型、ETF 范围、日期范围、参数版本、重试次数、错误信息和执行时间。

具体 Prisma 字段、索引、关系和数据库迁移必须在技术实现阶段确定。

## 18. Web 页面设计

### 18.1 页面清单

| 页面                          | 主要功能                 |
| ----------------------------- | ------------------------ |
| `/analysis`                   | ETF 分析总览、搜索和排序 |
| `/analysis/[code]`            | 单只 ETF 的完整统计分析  |
| `/analysis/[code]/indicators` | 技术指标及历史状态       |
| `/analysis/[code]/events`     | 单只 ETF 的事件研究      |
| `/analysis/compare`           | 多 ETF 横向比较          |
| `/analysis/data-quality`      | 数据质量问题查询         |
| `/analysis/jobs`              | 计算任务列表与执行状态   |
| `/analysis/jobs/[id]`         | 单个任务的详情和错误信息 |

实际路由可以结合现有 Next.js 项目调整，但必须覆盖以上功能。

### 18.2 单只 ETF 详情页

建议设置以下分区：

1. 基本信息与最新计算状态。
2. 历史行情和技术指标。
3. 收益与风险统计。
4. 趋势和波动率。
5. K 线形态及量价分析。
6. 连续涨跌、回撤与反弹。
7. 时间周期与自相关。
8. 事件研究结果。

### 18.3 页面通用要求

- 支持日期范围筛选。
- 指标展示时提供名称、参数和简要公式说明。
- 展示数据更新时间、计算版本和结果状态。
- 计算失败时展示明确错误信息。
- 无数据时显示空状态，不得使用虚构数据填充。
- 长列表采用分页。
- 支持导出筛选后的结果。
- 图表和表格必须使用后端预计算结果。

## 19. API 需求

API 以读取持久化结果为主，不承担全历史计算。

建议接口：

- `GET /api/analysis/etfs`：ETF 分析列表。
- `GET /api/analysis/etfs/:code/overview`：ETF 统计概览。
- `GET /api/analysis/etfs/:code/features`：日度特征及技术指标。
- `GET /api/analysis/etfs/:code/statistics`：收益与风险统计。
- `GET /api/analysis/etfs/:code/events`：事件研究结果。
- `GET /api/analysis/compare`：ETF 横向比较。
- `GET /api/analysis/data-quality`：数据质量结果。
- `GET /api/analysis/jobs`：计算任务列表。
- `GET /api/analysis/jobs/:id`：计算任务详情。
- `POST /api/analysis/jobs`：创建全量计算或重算任务。
- `GET /api/analysis/export`：导出已计算结果。

创建任务的接口只负责校验参数、登记任务并返回任务 ID，不应在 HTTP 请求生命周期内同步完成全历史计算。

所有接口必须定义参数校验、分页方式、错误响应和权限边界（如项目已有权限体系则复用）。

## 20. 非功能要求

### 20.1 正确性

- 所有指标使用统一公式和参数。
- 全量与增量结果在相同输入条件下保持一致。
- 指标初始化和缺失数据处理有明确规则。
- 历史修正后，受影响结果能够被识别和重算。
- 不得将未来信息泄漏到历史信号中。

### 20.2 性能

- 普通查询不遍历全部历史 K 线重新计算指标。
- 数据库查询应使用合适索引。
- 大型计算放入后台任务。
- 计算应支持按 ETF 分批执行。
- 首次全量初始化不阻塞 Web 页面正常访问。

### 20.3 可维护性

- 指标计算逻辑与 Next.js 页面分离。
- 指标公式和参数集中管理。
- 计算任务可追踪、可重试。
- 数据库迁移可重复部署。
- 重要计算逻辑有单元测试。
- 不引入没有明确需求的复杂基础设施。

### 20.4 安全性

- 所有用户输入必须校验。
- 不允许前端直接提交任意可执行代码作为本期计算逻辑。
- 任务接口需要限制重复提交和不合理的计算范围。
- 不得在错误信息中泄露数据库凭证等敏感信息。

## 22. Codex 开发实施要求

Codex 必须先检查现有仓库，再按照以下顺序开发：

**第一阶段：项目检查与数据验证**

检查现有 K 线数据、数据库、项目结构、运行方式和测试环境。确认前复权口径、日期字段和收益字段定义。

**第二阶段：数据模型与计算基础**

设计预计算结果、统计快照、事件研究和任务记录的数据模型，提供必要的 Prisma 迁移；实现基础特征和技术指标计算。

**第三阶段：预计算任务系统**

实现全量计算、增量计算、历史重算、任务状态、幂等处理、失败重试和结果发布。

**第四阶段：统计分析**

实现收益风险、趋势波动率、K 线形态、量价、连续涨跌、回撤、时间周期和事件研究。

**第五阶段：Web 页面与 API**

实现 ETF 总览、详情、比较、数据质量、事件研究、任务管理和结果导出。

**第六阶段：集成测试与验收**

验证公式正确性、历史修正传播、任务可靠性、全量增量一致性和页面查询性能。

每个阶段完成后，必须运行实际可用的测试、修复发现的问题，并更新开发进度。不得仅生成代码或文档就标记为完成。

如果文档与现有项目存在冲突，或某个金融计算定义尚未确定，应先记录冲突并提出明确的解决方案，不得自行猜测后直接实现。

1. 可运行的 Next.js Web 统计分析系统。
2. 预计算与后台任务模块。
3. 必要的 Prisma Schema 变更和数据库迁移。
4. 技术指标、统计分析和事件研究的计算实现。
