本次将系统设计明确为：TypeScript 在线策略编写 + 独立隔离执行环境 + 统一回测引擎。这意味着用户可以在 Next.js 网页中自行编写和修改策略，而不需要每新增一种策略就修改回测引擎。

同时保留现有项目约束：行情数据通过 Prisma 从数据库读取、使用前复权日 K 数据、仅做多、以收盘价进行模拟成交，并由统一引擎管理资金、持仓、手续费、订单和回测结果。

以下给出可以交给 Codex 实施的 PRD 与技术设计文档。策略执行环境、安全边界、策略 API、数据库设计和验收标准都会明确下来。

# 第一部分：产品需求文档 PRD V1.2

## 1. 产品定位

### 1.1 产品目标

构建一个用于 A 股 ETF 历史行情分析、量化策略开发和历史回测的本地 Web 应用。

用户可以在网页中编写 TypeScript 策略代码，选择 ETF、回测时间范围、初始资金及交易配置，运行历史回测，并通过收益曲线、交易记录、资产变化和风险指标评估策略表现。

系统采用通用策略架构。策略代码负责生成交易意图，统一回测引擎负责执行交易和资产核算。

新增策略原则上不需要修改回测引擎。

### 1.2 核心目标

1. 直接读取现有 Prisma 数据库中的 ETF 和日 K 数据。
2. 对 ETF 历史行情进行统计分析和技术指标分析。
3. 提供在线 TypeScript 策略编辑器。
4. 提供安全、受限的策略隔离执行环境。
5. 建立统一的订单执行和回测引擎。
6. 支持单 ETF 和多 ETF 策略回测。
7. 提供回测报告、基准比较、策略版本管理。
8. 保证回测结果可复现，并能追踪策略、数据和参数版本。

### 1.3 非目标

第一阶段不实现：

- 实盘交易和券商下单。
- 实时行情交易。
- 分钟 K、Tick 级别回测。
- 做空、融资、杠杆和期权交易。
- CSV 行情导入或 CSV 作为行情主数据源。
- 让策略代码直接操作数据库、账户或文件系统。
- 让用户编写任意 Node.js 服务端程序并直接运行。

## 2. 核心设计原则

### 2.1 策略与引擎分离

系统必须分离以下职责：

- **策略代码**：读取允许访问的行情和账户快照，计算交易条件，返回交易意图。
- **策略运行环境**：隔离运行用户编写的代码，限制权限和资源。
- **回测引擎**：控制回测时间、交易时序、订单校验、成交和资产核算。
- **数据层**：通过 Prisma 读取行情，管理策略、版本和回测结果。
- **分析层**：计算收益、回撤、波动率、交易统计等指标。
- **Web 层**：提供策略编辑、配置、运行和结果展示。

策略不能修改回测引擎内部状态，也不能绕过订单执行器。

### 2.2 单一行情数据入口

所有 ETF 元数据和 K 线数据均来自现有 Prisma 数据库。

禁止在系统中增加以下作为必要流程的功能：

- CSV 上传。
- CSV 行情解析。
- CSV 导入任务。
- 依赖外部文件维护行情。

统一通过行情 Repository 访问数据库。策略执行环境不得直接连接 SQLite。

### 2.3 回测规则统一

无论使用哪种策略，都必须遵守同一套规则：

- 仅做多。
- 使用日 K 数据。
- 使用前复权价格作为研究价格。
- 采用统一的收盘价模拟成交规则。
- 不允许负现金、负持仓或借钱。
- 统一计算手续费、交易数量、成交记录和每日资产。
- 统一处理数据缺失、预热期和回测结束。
- 不允许策略自行修改费用或成交价格。

### 2.4 结果可复现

每次回测都必须记录：

- 策略 ID 和不可变的策略版本。
- 实际执行的策略代码快照或其内容哈希。
- 策略参数。
- ETF 范围和回测时间区间。
- 初始资金及费用配置。
- 价格模型和成交模型版本。
- 引擎版本。
- 行情数据版本或数据快照标识。
- 回测状态、开始时间、结束时间及错误信息。

如果底层 K 线后来被修正，系统必须能够识别新旧数据差异，不能把新数据回测结果误认为旧回测结果。

## 3. 用户与主要使用流程

8. 查看回测进度和日志。
9. 分析收益曲线、最大回撤、交易记录和每日资产。
10. 修改策略后保存新版本，再次回测并比较结果。

## 4. 行情数据要求

### 4.1 现有数据模型

以当前项目中的 Prisma Schema 和实际 SQLite 数据库为准。已知现有模型包括：

```
model Etf {
  code          String @id
  name          String
  trackingIndex String
  trackIndex    String
  scale         Float

  @@map("etf")
}

model Kline {
  code          String
  date          Int
  open          Float
  high          Float
  low           Float
  close         Float
  volume        Float
  amount        Float
  change        Float
  changePercent Float

  @@id([code, date])
  @@unique([code, date])
  @@index([code, date])

  @@map("kline")
}
```

以上仅用于描述已知结构。开发前必须检查实际 Schema、数据库迁移历史、Prisma 版本及现有数据。

不得擅自重命名 `trackingIndex`、`trackIndex` 等字段，不得直接重建或清空现有数据库。

### 4.1.1 当前项目现状（已核对）

以下为对现有代码与 SQLite 数据库的实际核对结果，作为实施基线：

- 技术栈实测版本：Next.js 16.4.1（App Router）、React 19.3.0、TypeScript 5、Prisma 5.22.0（`prisma` 与 `@prisma/client` 均解析为 5.22.0）。
- Prisma Schema 位于 `services/prisma/schema.prisma`，客户端封装在 `services/prisma/index.ts`（惰性实例化的单例）。
- SQLite 数据库为 `services/prisma/dev.db`，连接串 `DATABASE_URL="file:./dev.db"`。
- 数据库中实际只有 `etf` 与 `kline` 两张业务表。Schema 顶部注释提到的 “subscribeShare 原始快照、同步任务状态” 等模型当前并不存在，实施以实际表结构为准。
- `kline.date` 为 `Int`，格式为 `YYYYMMDD`（例如 `20261015`），不是 ISO 日期字符串或毫秒时间戳。
- 现有数据规模：ETF 24 条，K 线 29428 行，K 线区间约 `20120528` 至 `20261015`（每只 ETF 覆盖范围不同）。
- 项目**没有** `prisma/migrations` 目录，也没有迁移历史；`package.json` 仅提供 `db:generate`（`prisma generate`）与 `db:push`（`prisma db push`）。**本项目决定继续使用 `db push`**（见 14.1）。
- `services/crawler/kline.ts` 的 `adjust=1` **已确认为前复权**，数据库中 `kline` 的 OHLC 即前复权价格（见 4.3）。
- 路径别名 `@/*` 映射到项目根目录 `./*`（见 `tsconfig.json`），模块导入形如 `@/services/...`。
- 项目当前**没有**测试框架或 `test` 脚本，也没有可用测试依赖（无 Jest/Vitest）。

### 4.2 行情读取要求

行情 Repository 必须支持：

- 按 ETF 代码查询。
- 按开始日期和结束日期查询。
- 日期入参与返回统一使用 `YYYYMMDD` 整数格式，与 `kline.date` 保持一致。
- 按日期升序返回 K 线。
- 查询回测区间之前的指标预热数据。
- 检查重复日期、缺失数据、非法价格和 OHLC 关系。
- 检查成交量、成交额等字段是否存在异常。
- 识别同一 ETF 的行情是否发生变化。

查询必须有明确的日期范围和合理的资源限制。

### 4.3 前复权价格规则

第一阶段统一使用数据库中已经存储的前复权价格进行研究和回测。

要求：

- 技术指标使用前复权 OHLC 数据。
- 收益分析使用同一套前复权价格。
- 回测成交价格使用前复权收盘价。
- 每日持仓估值使用前复权收盘价。
- 不混用原始价格与前复权价格计算同一条收益曲线。

必须明确：前复权价格会因未来分红、拆分等公司行为而改变。它适合用于统一的历史研究模型，但不是历史真实成交价格，也不等于真实账户的现金和持仓变化。

本系统第一阶段属于**研究型回测**，不宣称精确还原历史实际交易。

**数据来源说明：** 现有 K 线由 `services/crawler/kline.ts` 从外部接口拉取，请求参数为 `period=day&adjust=1`，并以 `upsert` 覆盖写入 `kline` 表。`adjust=1` **已确认为前复权**，本节“前复权价格”假设成立。需注意：

- 覆盖写意味着“前复权”历史会随公司行为整体重算，同一 ETF 的既有 K 线会被改写。必须依赖数据指纹（见 2.4、8、14.2 的 `dataFingerprint`）识别差异，避免把改写后的新数据误当作旧回测结果。

### 4.4 行情采集链路与 ETF 范围

- 行情写入只由现有采集服务完成：`services/crawler`（`etfs.ts`、`kline.ts`、`index.ts`）配合路由 `app/api/crawler/route.ts`。
- ETF 范围由 `services/crawler/etfs.ts` 内的**硬编码白名单**（一组 `trackIndex` 加 `510300.SH`）决定，当前仅覆盖 24 只 ETF，系统没有 ETF 手工新增或编辑入口。
- 因此 `/etfs`、ETF 比较、多 ETF 回测等功能都应基于这批受控 ETF 设计，不能按“全市场任意 ETF”假设实现。
- 当前没有同步任务状态表或数据版本表；2.4 与 8 要求的数据版本 / 数据指纹需要新增机制，例如对回测区间内的 K 线做内容哈希并写入 `BacktestRun.dataFingerprint`。

## 5. 通用策略系统需求

### 5.1 策略语言

第一阶段仅支持 TypeScript 策略代码。

用户可以：

- 创建策略。
- 编写和编辑代码。
- 配置策略参数。
- 检查语法和接口。
- 运行试验回测。
- 保存新版本。
- 复制、归档策略。
- 查看历史回测记录。

策略代码必须实现系统定义的统一接口。

### 5.2 策略能力

策略应可以根据上下文：

- 读取当前允许访问的 K 线。
- 读取历史 K 线。
- 计算或读取技术指标。
- 读取当前现金和持仓快照。
- 读取策略参数。
- 生成买入、卖出或持有意图。
- 在多 ETF 模式下为不同 ETF 生成交易意图。
- 输出可追踪的策略日志。

### 5.3 策略限制

策略不得：

- 直接修改现金、持仓或账户总资产。
- 直接生成已成交交易记录。
- 自行决定最终成交价格。
- 自行修改手续费配置。
- 直接访问 Prisma 或 SQLite。
- 直接访问网络、操作系统环境变量或任意文件。
- 读取当前决策时点之后的行情。
- 使用未声明的外部模块。
- 通过无限循环或超大计算量拖垮系统。
- 绕过订单执行器执行交易。

### 5.4 策略运行方式

采用独立隔离执行环境。

推荐架构：

- Next.js 负责 Web 页面、配置和任务管理。
- 回测服务负责调度和执行回测。
- 策略运行器负责运行用户代码。
- 策略运行器与 Web 服务、数据库服务之间使用受限的数据协议通信。

策略运行器应运行在独立进程或容器中，并具备操作系统层面的权限隔离、资源限制及网络访问限制。

**不能把 `eval`、`new Function`、普通 `try/catch` 或仅仅使用 Node.js Worker 视为安全沙箱。**

具体隔离技术须在技术选型阶段验证。独立进程不自动等于安全隔离；必须限制文件、网络、环境变量、进程创建、CPU、内存和运行时间。无法满足安全条件时，不应允许执行用户策略。

## 6. 回测功能需求

### 6.1 基础配置

每次回测至少需要：

- 策略版本。
- 一个或多个 ETF。
- 回测开始日期。
- 回测结束日期。
- 初始资金。
- 手续费参数。
- 交易单位规则。
- 成交模型。
- 策略参数。

具体交易费率、ETF 交易单位及费用下限应配置化，不能将所有 ETF 的规则写死成同一组常量。

### 6.2 交易规则

- 只允许买入和卖出已有 ETF。
- 不允许做空。
- 买入数量必须满足交易单位要求。
- 卖出数量不能超过持仓。
- 不允许负现金。
- 手续费由引擎统一计算。
- 订单执行结果必须可追踪。
- 资金不足时，按配置的订单优先级处理；不能满足合法交易单位时，跳过订单并记录原因。
- 交易失败不得修改持仓和现金。

对于同日多个 ETF 的订单，必须按明确的订单优先级处理，不能依赖异步执行顺序。

### 6.3 成交时序

系统采用用户指定的日 K 收盘价模拟成交模型。

必须区分两个概念：

1. 策略在当日收盘价确定后，使用当日完整 K 线计算信号。
2. 系统假设订单以当日收盘价成交。

这是用户接受的研究型简化模型。由于当日最终收盘价只有收盘后才能确定，实际市场通常不能保证在知道最终收盘价后再以同一价格成交。

因此，报告必须显示成交模型为“当日收盘价理想化模拟”，不得宣称真实可执行。

未来如需更严格的无前视偏差模型，可以增加“当日收盘后生成信号，下一交易日开盘或其他可执行价格成交”的模式，但不属于第一阶段必需功能。

### 6.4 回测结果

每次回测必须生成：

- 初始资金。
- 最终现金。
- 最终持仓数量。
- 最终持仓市值。
- 最终总资产。
- 总收益金额。
- 总收益率。
- 年化收益率。
- 最大回撤。
- 年化波动率。
- 夏普比率（明确无风险利率配置）。
- 交易次数。
- 盈利交易比例。
- 平均盈利与平均亏损。
- 总手续费。
- 每日资产记录。
- 完整订单与成交记录。
- 策略日志和异常记录。

指标不适用或数据不足时，应显示为空值及原因，不能静默显示为 0。

### 6.5 期末持仓

默认在回测结束时按结束日期收盘价对剩余持仓估值，不自动虚构一笔卖出交易。

如果用户选择期末清仓，则按照指定的模拟成交规则记录清仓交易及相关手续费。

## 7. 内置示例策略

系统应内置示例策略，作为接口演示和用户编写策略的参考。

| 策略         | 规则示例                           |
| ------------ | ---------------------------------- |
| 买入持有     | 首次符合条件时买入，之后持有       |
| 均线交叉     | 短均线上穿长均线买入，下穿卖出     |
| 布林带       | 价格上穿下轨买入，向下穿越中轨卖出 |
| MACD         | DIF 上穿 DEA 买入，下穿 DEA 卖出   |
| 固定金额定投 | 按预设交易日投入固定金额           |
| 趋势过滤     | 根据趋势指标决定是否允许买入       |

这些策略仅用于验证通用策略系统，不应成为回测引擎中的硬编码分支。

## 8. 策略版本与回测记录

- 策略每次保存修改都创建新版本。
- 已被回测引用的策略版本不可原地覆盖。
- 回测记录必须绑定策略版本。
- 回测记录必须保存参数快照。
- 已完成的回测结果不因后续策略修改而变化。
- 行情数据发生变化时，应显示数据版本差异或提示结果不可直接复现。
- 删除策略时，应优先采用归档方式，保留关联回测记录。

## 9. 验收标准

### 行情数据

- ETF 和 K 线均通过 Prisma 查询。
- 无 CSV 导入依赖。
- K 线按日期升序。
- 日期范围查询准确。
- 指标预热数据不计入回测区间交易。
- 异常行情有可追踪的校验结果。

### 策略编辑器

- 能创建、编辑、校验和保存 TypeScript 策略。
- 不符合接口的策略不能运行。
- 参数不合法时有明确提示。
- 保存后生成新版本。
- 策略可以输出买入、卖出、持有意图。

### 隔离执行

- 策略无法直连数据库。
- 策略无法任意访问网络和文件。
- 策略无法读取服务器秘密信息。
- 超时或资源超限可以终止执行。
- 运行失败不会破坏 Next.js 服务或数据库。
- 无法满足隔离要求时，系统拒绝执行策略。

### 回测引擎

- 现金和持仓不会为负。
- 手续费不会重复扣除。
- 非法交易单位会被拒绝。
- 资金不足会记录跳过原因。
- 同日多 ETF 订单按固定优先级执行。
- 每笔交易都有完整记录。
- 每日资产能够核对现金与持仓市值。
- 期末持仓按所选规则处理。
- 相同策略版本、参数、行情和引擎配置可复现相同结果。

## 11. 通用策略 API 设计

### 11.1 策略定义

策略是用户编写的代码，不是回测引擎的子类。

策略需要实现系统规定的接口，返回符合协议的交易意图。

建议提供以下概念：

- `defineStrategy`：声明策略名称、说明、参数及生命周期。
- `initialize`：回测开始时初始化策略状态。
- `onBar`：每个模拟交易日执行一次或按组合调度规则执行。
- `onOrderUpdate`：可选，接收已经执行或被拒绝的订单结果。
- `onFinish`：可选，回测结束时执行只读汇总逻辑。

第一阶段可以先实现 `initialize` 和 `onBar`。其余生命周期在接口确有需要时再扩展。

### 11.2 策略接口示例

以下为接口设计示意，Codex 应根据最终的 TypeScript 类型文件实现并统一版本。

```
type StrategyAction = "buy" | "sell" | "hold";

type OrderIntent = {
  code: string;
  action: StrategyAction;
  quantity?: number;
  percent?: number;
  reason?: string;
};

type StrategyResult = {
  orders: OrderIntent[];
  logs?: string[];
};

type StrategyDefinition<P> = {
  name: string;
  description?: string;
  version?: string;
  params: P;

  initialize?: (
    ctx: StrategyInitContext<P>
  ) => void;

  onBar: (
    ctx: StrategyContext<P>
  ) => StrategyResult;
};
```

约束：

1. `quantity` 与 `percent` 只能使用一种，不能同时提供。
2. `percent` 必须限制在合法范围内，具体范围和含义由统一接口定义。
3. `hold` 不应产生交易订单。
4. 买卖意图只表示请求，不代表成交成功。
5. `code` 必须属于当前回测允许的 ETF 集合。
6. 不允许策略自定义价格、手续费、成交时间或直接改账户。
7. 返回值必须经过运行时 Schema 校验。
8. 非法返回值应拒绝执行，并写入错误日志。

参数 Schema 必须同时支持编辑器提示和运行时验证。类型检查不能代替运行时校验。

### 11.3 策略上下文

建议为策略提供以下只读上下文：

```
type StrategyContext<P> = {
  date: number;

  bar: {
    code: string;
    date: number;
    open: number;
    high: number;
    low: number;
    close: number;
    volume: number;
    amount: number;
  } | null;

  history: {
    getBars: (
      count: number
    ) => readonly HistoricalBar[];
  };

  indicators: IndicatorAPI;

  position: PositionSnapshot;

  account: AccountSnapshot;

  params: Readonly<P>;
};
```

以上仅为概念性定义。实现时应使用实际项目中的日期类型和指标 API 类型，避免不必要的数据复制和过大消息。

上下文中的账户和持仓均为只读快照。不能暴露 Prisma Client、数据库事务对象、文件句柄、网络客户端、进程对象或宿主运行环境对象。

历史数据 API 必须保证只能访问当前决策时点允许使用的数据。

### 11.4 策略状态

策略可能需要记录状态，例如：

- 是否已完成首次买入。
- 最近一次信号。
- 分批买入次数。
- 最高持仓价格。
- 策略内部的趋势状态。

状态必须有明确的序列化规则。

第一阶段可限制为 JSON 可序列化的数据类型。不能依赖闭包、全局变量或进程残留状态来保存策略进度。

每次回测启动时都要初始化状态；不同回测之间不能共享可变策略状态。

## 12. 策略编译、校验与隔离执行

### 12.1 处理流程

```
用户提交 TypeScript
        │
        ▼
代码大小及基础校验
        │
        ▼
TypeScript 语法与类型检查
        │
        ▼
检查导出入口和策略接口
        │
        ▼
可信编译器转换为受支持的 JavaScript
        │
        ▼
策略运行器加载代码
        │
        ▼
受限上下文和输入数据
        │
        ▼
执行 onBar
        │
        ▼
校验返回结果
        │
        ▼
回测引擎决定是否执行订单
```

类型检查与运行时校验是两个不同步骤。即使 TypeScript 编译通过，也不能认为策略可信。

### 12.2 沙箱要求

策略运行器必须遵循最小权限原则。

**必须限制：**

- 网络访问。
- 文件系统访问。
- 环境变量和密钥访问。
- 子进程创建。
- 任意模块加载。
- 动态代码加载。
- CPU 时间。
- 内存使用。
- 单次执行时间。
- 单次返回的数据大小。
- 策略日志的总大小。

建议采用独立容器或具备等效操作系统级隔离能力的执行环境，并配合只读文件系统、禁用网络、低权限用户、资源配额和超时终止机制。

如果使用本地独立进程，应验证操作系统提供的权限限制能否满足上述要求。单纯启动子进程、使用 Worker 或删除几个全局变量，不足以作为完整的安全方案。

### 12.3 策略执行协议

建议使用结构化 JSON 消息在宿主与运行器之间传递数据。

输入包含：

- 协议版本。
- 策略代码版本标识。
- 当前交易日。
- 当前 K 线和允许访问的历史数据。
- 当前账户和持仓快照。
- 参数。
- 策略状态。

输出包含：

- 协议版本。
- 交易意图数组。
- 更新后的策略状态。
- 日志。
- 错误信息（如有）。

协议不得包含可直接访问宿主资源的对象引用。

### 12.4 失败处理

以下情况均应终止当前策略执行：

- 语法或类型检查失败。
- 导出接口不符合约定。
- 运行超时。
- 内存或计算量超限。
- 输出格式错误。
- 返回非法交易意图。
- 沙箱进程崩溃。
- 输入或输出超过限制。

策略执行失败时，不应提交该次调用产生的订单意图。已完成的历史成交是否保留，取决于回测任务的整体事务设计；第一阶段建议将该回测标记为失败，保留诊断信息，不展示为完整成功结果。

## 13. 回测引擎设计

### 13.1 引擎职责

回测引擎负责：

1. 加载回测配置。
2. 读取 ETF 和 K 线。
3. 校验行情完整性。
4. 加载预热数据。
5. 初始化账户、持仓及策略状态。
6. 按交易日调度策略。
7. 接收策略交易意图。
8. 按规则校验和执行订单。
9. 更新现金、持仓、成本和资产。
10. 记录每日状态。
11. 计算最终指标。
12. 保存完整回测结果。

策略代码不负责上述账户核算。

### 13.2 推荐模块

| 模块                   | 职责                   |
| ---------------------- | ---------------------- |
| `MarketDataRepository` | 通过 Prisma 查询行情   |
| `MarketDataValidator`  | 检查行情质量           |
| `IndicatorService`     | 计算技术指标           |
| `StrategyCompiler`     | 检查并转换策略代码     |
| `StrategyRunner`       | 在隔离环境执行策略     |
| `BacktestScheduler`    | 管理日期和执行顺序     |
| `OrderValidator`       | 检查交易请求           |
| `BrokerSimulator`      | 模拟成交和手续费       |
| `PortfolioManager`     | 管理现金、持仓和成本   |
| `MetricsCalculator`    | 计算收益和风险指标     |
| `BacktestRecorder`     | 保存每日记录和交易明细 |

### 13.3 单日执行流程

建议将单日流程明确为：

1. 读取当日允许使用的行情。
2. 为策略构造只读上下文。
3. 执行策略，取得交易意图。
4. 校验所有交易意图。
5. 按确定的订单优先级依次处理。
6. 根据当日收盘价模型模拟成交。
7. 扣除手续费并更新持仓和现金。
8. 按当日收盘价估值。
9. 记录每日资产、持仓、交易和日志。

同日多 ETF 交易必须有固定顺序。如果资金不足，后续订单可能被跳过。该行为需要在回测配置及结果中明确记录。

### 13.4 资金与持仓核算

至少维护：

- `cash`：可用现金。
- `quantity`：持仓数量。
- `averageCost`：持仓加权平均成本。
- `marketValue`：当前持仓市值。
- `totalAssets`：总资产。
- `realizedPnl`：已实现盈亏。
- `unrealizedPnl`：未实现盈亏。
- `fees`：手续费累计值。

核心核算关系：

`总资产 = 现金 + 持仓市值`

买入和卖出均由统一的模拟经纪模块完成。手续费只扣除一次，不能在策略、订单执行器和资产记录中重复计算。

对于前复权价格模型，成本和收益仅代表该研究模型中的计算结果，不得解释为真实账户的历史成交成本。

**数值精度：** 数据库中的价格、成交额等字段是 SQLite `REAL`（Prisma `Float`）。资金核算不应直接长期累加浮点数，否则会出现小数漂移、对账不平。引擎内部应显式选定一种表示并统一使用，例如以“分”为单位的整数、或统一到固定小数位并在比较时使用容差，并在测试中验证 `总资产 = 现金 + 持仓市值` 在长序列后仍然成立。

### 13.5 收益指标

日收益率可按连续交易日的资产变化计算：

`dailyReturn = totalAssets[t] / totalAssets[t-1] - 1`

对于没有外部资金流入的策略，累计收益率可以使用期末总资产与初始资产计算。

年化收益率、年化波动率和最大回撤应采用统一的指标定义。年化计算可以使用 252 个交易日的约定，并在报告中注明。

固定金额定投涉及外部资金流入，不能直接用期末总资产除以最初资金来计算投资收益率。至少需要同时记录：

- 初始资金。
- 累计追加资金。
- 累计投入金额。
- 期末总资产。
- 盈亏金额。

如要计算可与其他策略直接比较的资金流敏感收益率，应进一步实现现金流加权或时间加权收益率，并清楚标注所用方法。

## 14. 数据库设计

### 14.1 设计原则

- 保留现有 `Etf` 和 `Kline` 模型。
- 不把策略代码混入 K 线数据表。
- 策略版本不可变。
- 回测结果与策略版本建立明确关联。
- 通过 Prisma Schema 演进数据库。
- 不因增加回测模块而清空现有数据。

**迁移方式（已确定）：** 当前项目没有 `prisma/migrations` 历史，实际使用 `prisma db push`，本项目**继续使用 `db push`** 演进 Schema，不引入 `prisma migrate`。

- 新增 `Strategy*`、`Backtest*` 等模型后，通过 `prisma db push` 应用变更。
- `db push` 不做增量迁移、无回放历史，因此每次改 Schema 前必须先备份 `services/prisma/dev.db`，并避免对现有 `etf` / `kline` 表做破坏性重写或清空。
- 新增模型应为纯新增（新表 / 新列），不改动现有两表的字段含义与主键。

### 14.3 数据一致性

- 订单和每日记录均关联到回测任务。
- 运行失败必须保留错误状态。
- 完成状态只能在必要的结果记录成功保存后设置。
- 回测结果必须引用明确的策略版本。
- 关键数据写入应使用适当的事务或可恢复的任务状态机制。

## 必须遵守的要求

2. 行情数据只从现有 Prisma 数据库读取，不开发 CSV 导入流程。

12. 不要一次性开发所有模块；每个阶段完成后先运行测试，再继续下一阶段。

## 实施时特别注意的三个问题

1\. 安全隔离是独立的工程任务。 用户策略代码属于不可信代码，建议把运行器当作独立服务设计。即使应用只在本地运行，也不应默认用户编写的代码是安全的。

2\. 策略 API 要先稳定，再开发编辑器。 应先通过内置策略验证 API、订单协议和回测引擎，再接入在线编辑器，避免后续频繁修改策略接口。

3\. 收盘价成交与前复权价格都属于研究模型。 报告必须展示这两项假设，并将回测收益与真实历史账户收益区分开来。
