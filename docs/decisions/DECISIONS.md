**文档名称：** decisions/DECISIONS.md  
**产品版本：** V0.6  
**文档状态：** 已确认决策汇总  
**适用对象：** Codex、开发人员

## 1. 文档目的

本文档集中记录 ETF 分析系统 V0.6 的重要产品、业务、技术和数据决策。

主要目的：

1. 防止开发过程中反复讨论已经确认的事项。
2. 防止 Codex 擅自改变产品范围。
3. 防止不同模块采用不一致的计算口径。
4. 记录尚未验证的数据源信息。
5. 为后续版本提供决策依据。

### 1.1 决策状态

每项决策使用以下状态：

| 状态   | 含义                       |
| ------ | -------------------------- |
| 已确认 | 已明确决定，开发必须遵守   |
| 待实测 | 需要通过真实接口或数据验证 |
| 待决策 | 当前没有足够信息确定方案   |
| 已废弃 | 曾经讨论，但已经不再采用   |

### 1.2 决策修改原则

已确认决策不能因为实现方便而擅自修改。

确实需要调整时：

1. 说明原决策。
2. 说明调整原因。
3. 分析影响范围。
4. 提出新方案。
5. 记录决策变更。
6. 同步修改相关设计文档。

# 2. 产品决策

## D001：产品定位

<badge color="success">已确认</badge>

产品定位为 ETF 每日数据分析与表现排名系统。

核心目标：

- 观察整个 ETF 研究池的表现。
- 比较 ETF 的收益、风险、趋势、成交和估值。
- 观察不同 ETF 分类的整体表现。
- 观察市场整体状态。
- 保留每日分析结果，支持历史查看。

不以自动交易、策略回测或交易信号为核心目标。

## D002：产品功能范围

<badge color="success">已确认</badge>

V0.6 包含以下十项功能：

1. ETF 研究池管理。
2. 行情与估值采集。
3. ETF 特征计算。
4. 全池排名。
5. 市场概览。
6. ETF 全量列表。
7. 分类表现。
8. 历史分析结果。
9. 本地每日任务。
10. 静态前端部署。

## D003：前端页面数量

<badge color="success">已确认</badge>

V0.6 只建设三个页面：

| 页面         | 路由          | 默认状态 |
| ------------ | ------------- | -------- |
| ETF 全量列表 | `/etfs`       | 默认首页 |
| 市场概览     | `/market`     | 非默认   |
| 分类表现     | `/categories` | 非默认   |

不建设 ETF 详情页、独立研究报告页、回测页和复杂管理后台。

## D004：全池排名优先

<badge color="success">已确认</badge>

所有 ETF 在同一个研究池中统一计算和排名。

分类只是观察和筛选维度，不影响：

- ETF 特征计算。
- 全池排名。
- 市场整体统计。

分类内部排名由前端从全池结果中筛选后动态展示。

## D005：不生成买卖建议

<badge color="success">已确认</badge>

系统生成描述性分析结论，不生成直接买入、卖出或仓位建议。

结论必须能够追溯到具体指标。

## D006：不使用加权综合评分

<badge color="success">已确认</badge>

V0.6 不启用未经验证的加权综合评分。

不同指标分别排名和展示。

未来如需引入综合评分，必须先评估：

- 指标之间的相关性。
- 对未来 5/20/60 日收益的预测能力。
- 样本外表现。
- 不同市场环境下的稳定性。

不能直接主观指定权重。

# 3. ETF 研究池决策

## D007：研究池筛选规则

<badge color="success">已确认</badge>

ETF 必须满足：

- `securityCode` 非空。
- `securityName` 非空。
- `trackIndex` 非空。
- 名称不包含“短融”。
- 名称不包含“债”。
- 规模不低于 3 亿元。
- 规模不能为空。
- 当成交额有效且小于 1500 万元时排除。

成交额为空或无法解析时，不因成交额条件排除。

## D008：跟踪指数去重

<badge color="success">已确认</badge>

同一个 `trackIndex` 只保留一只 ETF。

选择顺序：

1. 规模最大。
2. 规模相同时，成交额较大。
3. 规模和成交额相同时，ETF 代码升序。

最终研究池：

- 规模降序。
- ETF 代码升序。

## D009：字段含义

<badge color="success">已确认</badge>

| 字段          | 含义         |
| ------------- | ------------ |
| securityCode  | ETF 代码     |
| securityName  | ETF 名称     |
| scale         | ETF 规模     |
| trackingIndex | 跟踪指数名称 |
| trackIndex    | 跟踪指数代码 |
| premiumRate   | 溢价率       |
| amount        | 成交额       |

注意：

- `trackingIndex` 是指数名称。
- `trackIndex` 是指数代码。
- 估值使用指数代码关联。
- 原始 `trackingIndex` 允许为空，内部模型也必须允许为空。
- `trackIndex` 是研究池必需字段。

## D010：分类管理

<badge color="success">已确认</badge>

- 每只 ETF 必须且只能有一个二级分类。
- 分类建议可以自动生成。
- 分类结果需要人工确认。
- 待确认 ETF 不直接归入“其他”。
- 分类映射通过 JSON 文件维护。
- 不建设在线分类审批页面。
- 分类变更不触发特征计算和排名重算。

## D011：分类判断依据

<badge color="success">已确认</badge>

分类优先依据：

1. 指数正式名称。
2. 指数编制方案。
3. 指数成分股。
4. 指数投资范围。
5. 指数实际代表的行业或主题。

不能只通过 ETF 名称中的关键词判断分类。

# 5. 行情数据决策

## D019：行情复权方式

<badge color="success">已确认</badge>

当前系统只使用前复权行情。

不同时维护前复权和后复权两套行情。

当前系统不建设独立的 `KlineRaw` 数据表。

## D020：Kline 数据结构

<badge color="success">已确认</badge>

```ts
interface Kline {
  code: string;
  date: number; // YYYYMMDD

  open: number;
  high: number;
  low: number;
  close: number;

  volume: number;
  amount: number;

  change: number;
  changePercent: number;
}
```

主键逻辑为：

```text
[code, date]
```

## D021：日 K 持久化

<badge color="success">已确认</badge>

日 K 主要在任务执行期间使用内存数据。

不长期保存完整的日 K 历史文件。

历史计算和修正需要通过重新获取历史行情完成。

为解决历史行情变化检测问题，允许保存最小必要的逐日行情校验摘要，见 D030。

## D022：周 K 和月 K

<badge color="success">已确认</badge>

周 K 和月 K 由日 K 聚合生成。

当前周期不区分临时值和最终值。

例如周二计算时，当前周 K 由周一和周二已有日 K 组成。

## D023：历史行情修正

<badge color="success">已确认</badge>

历史行情修正不能只重新计算发生变化的当天。

必须从最早受影响日期开始，重新计算后续受影响的：

- ETF 特征。
- 排名。
- 市场统计。
- 分析结论。

## D024：收益周期

<badge color="success">已确认</badge>

主要收益周期：

- 1 日。
- 5 日。
- 20 日。
- 60 日。
- 120 日。
- 250 日。
- YTD。

周期按照有效交易日计算。

<badge color="success">已确认</badge>

重点计算：

- MA5。
- MA10。
- MA20。
- MA60。
- MA120。

## D026：波动率

<badge color="success">已确认</badge>

计算周期：

- 20 日。
- 60 日。
- 120 日。

采用日收益率样本标准差乘以 \(\sqrt{250}\) 年化。

## D027：最大回撤

<badge color="success">已确认</badge>

计算周期：

- 20 日。
- 60 日。
- 120 日。
- 250 日。

基于收盘价计算。

结果使用负数表示。

数值越接近 0，表示回撤越小。

## D028：估值指标

<badge color="success">已确认</badge>

支持：

- PE。
- PB。
- PS。
- DID。

其中：

- PE/PB/PS 分别独立排名。
- 历史百分位来自上游近五年数据。
- 上游百分位从 0～100 转换为 0～1 保存。
- 缺失值为 null。
- PEG 不默认参与低估排名。
- DID 单独展示，不擅自定义含义。

## D029：排名规则

<badge color="success">已确认</badge>

排名维度：

| 维度 | 指标                          | 方向       |
| ---- | ----------------------------- | ---------- |
| 动量 | 5/20/60/120/250 日及 YTD 收益 | 降序       |
| 风险 | 20/60 日波动率                | 升序       |
| 风险 | 20/60/120 日最大回撤          | 原始值降序 |
| 成交 | 20 日平均成交额               | 降序       |
| 溢价 | premiumRate                   | 升序       |
| 估值 | PE 历史百分位                 | 升序       |
| 估值 | PB 历史百分位                 | 升序       |
| 估值 | PS 历史百分位                 | 升序       |

排名采用竞赛排名。

缺失值不参与排名。

不生成未经确认的综合评分。

# 7. 历史数据和文件决策

## D030：行情历史修正检测摘要

<badge color="success">已确认</badge>

由于系统不长期保存完整日 K，但又需要检测历史行情修正，因此采用逐日校验摘要方案。

建议文件：

```text
data/runtime/kline-checksums.json
```

记录每只 ETF 每个交易日的行情摘要。

示例：

```ts
interface KlineChecksum {
  code: string;
  date: number;
  hash: string;
}
```

摘要根据以下字段生成：

- open。
- high。
- low。
- close。
- volume。
- amount。
- change。
- changePercent。

当同一 ETF、同一日期的 hash 发生变化时，视为该日期行情发生修正。

处理规则：

1. 获取足够长度的历史日 K。
2. 生成本次逐日摘要。
3. 与已有摘要比较。
4. 找出发生变化的日期。
5. 确定最早受影响日期。
6. 重新计算该日期及之后的历史结果。
7. 更新校验摘要。

该方案不保存完整日 K，但保存了定位历史修正所需的最小信息。

如果某次采集没有覆盖完整历史区间，不能把未覆盖日期当作已删除或已变化。

## D031：每日分析结果

<badge color="success">已确认</badge>

每日结果必须自包含。

每个日期保存完整 ETF 分析结果和市场概览。

建议：

```text
public/data/
├── current.json
└── daily/
    ├── 20261113.json
    └── 20261114.json
```

历史结果不依赖当前研究池配置才能正确展示。

研究池变化不允许直接覆盖历史日期的 ETF 结果。

## D032：current.json

<badge color="success">已确认</badge>

`current.json` 与最新每日结果采用相同数据结构。

写入顺序：

1. 生成完整每日结果。
2. 校验结果。
3. 保存每日历史文件。
4. 更新 current.json。

每日历史文件写入失败时，不允许更新 current.json。

## D033：估值历史存储

<badge color="success">已确认</badge>

估值对象为指数，不是 ETF。

同一个指数的 ETF 共享估值数据。

按指数代码拆分 JSON 文件。

例如：

```text
public/data/valuation/000300.json
```

采用指数代码、日期和估值类型作为记录唯一标识。

历史估值不能因为某次上游未返回数据而被删除。

PE、PB、PS 采集状态相互独立。

## D034：JSON 写入

<badge color="success">已确认</badge>

重要 JSON 文件必须使用安全写入。

流程：

1. 生成完整内容。
2. 写入临时文件。
3. 解析并校验。
4. 原子替换正式文件。
5. 必要时保留旧文件备份。

不允许直接逐段覆盖正式文件。

- 历史百分位是否始终在 0～100。
- 是否支持近五年数据。
- DID 的实际定义和单位。
- PEG 是否返回。

## V004：估值数据完整性

<badge color="warning">待实测</badge>

需要验证：

- 同一指数的 ETF 是否共享同一估值。
- 不同估值类型的日期是否一致。
- 是否存在缺失交易日。
- 是否存在历史估值修正。
- 是否需要按指数代码拆分请求。

# 10. 待明确的工程事项

以下事项不改变产品方向，但需要在开发实现中明确具体方案。

## E001：数据目录的唯一存储与发布策略

<badge color="warning">待明确</badge>

当前架构同时存在：

- `data/`
- `public/data/`

必须明确它们之间的同步规则。

要求：

- 本地任务工作数据只有一套权威来源。
- 前端静态发布目录不能成为另一套独立业务数据源。
- 不允许两个目录长期出现无法解释的数据差异。
- 同步失败时不能发布不完整的 current.json。

建议采用单一权威数据目录，并通过统一存储模块管理前端发布副本。

## E002：历史日期索引

<badge color="warning">待明确</badge>

前端需要知道有哪些历史分析日期。

V0.6 可以通过生成日期索引 JSON 实现，例如：

```text
public/data/dates.json
```

该文件记录已经生成的历史分析日期。

不能让前端直接读取服务器目录列表。

## E003：历史结果重算输入

<badge color="warning">待明确</badge>

由于不保存完整历史日 K，历史修正时必须重新获取所需历史行情。

需要明确：

- 每次请求的历史范围。
- 指定日期重算所需的前置行情长度。
- 如何保证计算所需的历史窗口完整。
- 数据源历史范围不足时如何处理。

不能只获取指定日期当天的数据就重新计算。

## E004：静态部署更新

<badge color="warning">待明确</badge>

需要确定静态托管平台和 JSON 更新方式。

要求：

- 支持更新 current.json。
- 支持增加每日历史文件。
- 支持更新被修正的历史文件。
- 更新后缓存策略正确。
- 前端不能读取到不完整的新旧混合结果。
