# ETF 数据采集设计文档

**文档名称：** DATA-SOURCE.md  
**产品版本：** V0.6  
**文档状态：** 设计规范已确定，接口细节以实际验证为准  
**适用对象：** Codex、开发人员

---

## 1. 设计目标

本模块负责为 ETF 分析系统提供稳定、标准化的数据输入。

系统需要采集三类核心数据：

1. ETF 基础信息。
2. ETF 前复权日 K 线。
3. ETF 跟踪指数估值数据（PE、PB、PS）。

采集的数据交给研究池模块和计算引擎使用。

本模块负责：

- 数据源接入。
- 接口请求。
- 原始数据解析。
- 字段标准化。
- 数据校验。
- 缺失数据处理。
- 异常数据处理。
- 采集失败处理。
- 历史数据重新采集。
- 数据更新状态记录。

本模块不负责：

- ETF 研究池筛选。
- ETF 分类。
- ETF 特征计算。
- ETF 排名。
- 市场统计。
- 前端页面展示。

## 2. 数据源总体规划

### 2.1 数据类型

| 数据类型     | 采集对象 | 用途       | 是否长期保存       |
| ------------ | -------- | ---------- | ------------------ |
| ETF 基础信息 | ETF      | 生成研究池 | 保存研究池结果     |
| ETF 日 K 线  | ETF      | 特征计算   | 不长期保存原始日 K |
| 指数估值     | 跟踪指数 | 估值分析   | 长期保存           |

### 2.2 数据源适配器

不同数据源必须通过独立适配器接入。

建议接口：

```ts
interface DataSource<T> {
  fetch(params: unknown): Promise<T>;
}
```

建议模块：

```text
src/
└── data-sources/
    ├── etf-basic/
    │   ├── client.ts
    │   ├── parser.ts
    │   └── types.ts
    │
    ├── etf-kline/
    │   ├── client.ts
    │   ├── parser.ts
    │   └── types.ts
    │
    └── index-valuation/
        ├── client.ts
        ├── parser.ts
        └── types.ts
```

要求：

- 接口请求和业务计算分离。
- 原始响应解析和标准数据转换分离。
- 不允许计算引擎直接依赖上游接口字段。
- 更换数据源时，不应影响计算引擎和前端。
- 每种数据源必须有独立的错误处理。
- 不允许把未验证的接口响应结构写成固定假设。

## 3. ETF 基础信息采集

### 3.1 采集目标

获取市场 ETF 候选列表，为研究池生成提供基础数据。

采集字段：

```ts
interface OriginalEtf {
  securityName: string;
  securityCode: string;
  scale: number | null;
  trackingIndex: string | null;
  trackIndex: string | null;
  premiumRate: string | number | null;
  amount: string;
}
```

字段说明：

| 字段          | 说明         | 处理要求              |
| ------------- | ------------ | --------------------- |
| securityName  | ETF 名称     | 转换为字符串          |
| securityCode  | ETF 代码     | 保留字符串和前导零    |
| scale         | ETF 规模     | 转换为 number 或 null |
| trackingIndex | 跟踪指数名称 | 保留原始名称          |
| trackIndex    | 跟踪指数代码 | 保留字符串            |
| premiumRate   | 溢价率       | 转换为 number 或 null |
| amount        | 成交额       | 转换为 number 或 null |

### 3.2 数据源

使用项目当前确认的 ETF 基础信息数据源。

数据源地址、请求参数和响应字段必须以实际接口验证结果为准。

在接口适配器中集中管理：

- 请求 URL。
- 请求参数。
- 请求 Header。
- 超时时间。
- 分页参数（如果接口支持分页）。
- 原始响应结构。
- 字段映射规则。

不得在研究池筛选代码中直接请求上游接口。

### 3.3 字段标准化

输出统一结构：

```ts
interface EtfBasicInfo {
  code: string;
  name: string;
  scale: number | null;
  trackingIndex: string | null;
  trackIndex: string | null;
  premiumRate: number | null;
  amount: number | null;
}
```

转换规则：

1. `securityCode` 转换为 `code`。
2. `securityName` 转换为 `name`。
3. 代码统一为字符串，不得转换为数字。
4. 空字符串转换为 null。
5. 无法解析的数值转换为 null。
6. 字符串 `"0"` 必须转换为数值 `0`。
7. `scale` 缺失时保留 null。
8. `amount` 缺失时保留 null。
9. 不得将 null 自动转换成 0。

### 3.4 单位验证

以下字段必须核实单位：

- `scale`
- `amount`
- `premiumRate`

要求：

- scale 统一转换为人民币元。
- amount 统一转换为人民币元。
- premiumRate 的百分比或小数口径必须明确。

如果上游规模单位为万元，转换为元时乘以 10000。

如果上游成交额单位为万元，转换为元时乘以 10000。

如果上游溢价率返回 0.02 表示 0.02%，必须保留其百分比含义，不能误转换成 2%。

单位转换只能在数据源适配器中执行一次，后续模块统一使用标准单位。

具体单位必须通过接口说明或实际样本核实，不允许猜测。

### 3.5 采集频率

ETF 基础信息在每日研究池更新任务中采集。

支持：

- 每日自动采集。
- 手动重新采集。
- 采集结果与上一版本对比。

### 3.6 异常处理

以下情况需要记录异常：

- 请求失败。
- 响应为空。
- 响应格式变化。
- ETF 代码缺失。
- 必要字段类型异常。
- 数值字段无法解析。
- 上游数据重复。

基础信息整体采集失败时，不允许将空结果覆盖当前有效研究池。

必须保留上一次有效数据，并使每日任务明确报告失败。

## 4. ETF 日 K 线采集

### 4.1 采集目标

采集研究池内每只 ETF 的历史日 K 线，为 ETF 特征计算提供行情数据。

统一采用前复权行情。

### 4.2 数据源

优先使用 AkShare 东方财富 ETF 历史行情接口：

```python
ak.fund_etf_hist_em(
    symbol="513500",
    period="daily",
    start_date="20200101",
    end_date="20261115",
    adjust="qfq"
)
```

参数说明：

| 参数       | 值       | 说明          |
| ---------- | -------- | ------------- |
| symbol     | ETF 代码 | 六位 ETF 代码 |
| period     | daily    | 日 K          |
| start_date | YYYYMMDD | 开始日期      |
| end_date   | YYYYMMDD | 结束日期      |
| adjust     | qfq      | 前复权        |

AkShare 文档中，`qfq` 表示前复权，`hfq` 表示后复权，空字符串表示不复权。<https://github.com/akfamily/akshare/blob/main/akshare/fund/fund_etf_em.py>

注意：

- `qfq` 是接口调用参数。
- 业务系统内部统一称为前复权。
- 不允许将不复权和后复权行情混入当前计算数据。
- 实际采集程序需要验证 AkShare 版本和返回字段。

### 4.3 标准 K 线结构

采集结果转换为：

```ts
interface Kline {
  code: string;
  date: number; // YYYYMMDD
  open: number;
  high: number;
  low: number;
  close: number;
  volume: number;
  amount: number;
  change: number;
  changePercent: number;
}
```

字段映射：

| 上游字段 | 内部字段      |
| -------- | ------------- |
| 日期     | date          |
| 开盘     | open          |
| 最高     | high          |
| 最低     | low           |
| 收盘     | close         |
| 成交量   | volume        |
| 成交额   | amount        |
| 涨跌额   | change        |
| 涨跌幅   | changePercent |

转换要求：

- date 转换为 YYYYMMDD 整数。
- 所有数值字段转换为 number。
- 不允许无效数字进入计算引擎。
- ETF 代码来自当前研究池。
- 同一 ETF 同一交易日期只能有一条 K 线。
- 按日期升序排列。

### 4.4 涨跌幅口径

上游涨跌幅必须验证单位。

内部 `changePercent` 统一采用百分数表示。

例如：

- 上涨 1% 保存为 `1`。
- 下跌 2.5% 保存为 `-2.5`。

如果上游已经采用百分数，不得重复乘以 100。

如果上游采用小数形式，则转换为百分数。

### 4.5 成交量和成交额口径

成交量和成交额需要分别保存。

- `volume`：沿用上游成交量数值和单位。
- `amount`：统一使用人民币元。

不得把成交量与成交额混淆。

成交量的份额、手等单位需要根据数据源实际返回结果确认，并记录在适配器说明中。

### 4.6 K 线数据校验

每条 K 线必须满足：

1. 日期格式合法。
2. OHLC 字段均为有效数值。
3. `high >= low`。
4. `high >= open`。
5. `high >= close`。
6. `low <= open`。
7. `low <= close`。
8. volume 不小于 0。
9. amount 不小于 0。

异常数据不得静默进入计算引擎。

对于不满足条件的记录：

- 记录 ETF 代码。
- 记录交易日期。
- 记录异常字段。
- 记录原始值。
- 将其标记为无效数据。

不得直接将异常行情修改成看似合理的数据。

### 4.7 历史行情采集

首次全量计算时，需要获取足够长的历史日 K 数据。

历史开始日期由系统配置决定。

必须覆盖计算引擎所需的最长统计周期，并额外保留足够的历史数据用于指标预热。

对于成立时间较短的 ETF，返回其实际可获取的历史数据。

不得人为补齐 ETF 成立前的数据。

### 4.8 每日行情采集

每日任务执行时：

1. 获取当前研究池。
2. 对研究池内每只 ETF 获取最新行情。
3. 检查最后一条 K 线日期。
4. 检查是否存在缺失交易日。
5. 识别最新行情是否已更新。
6. 将有效行情交给计算引擎。

行情采集需要支持：

- 首次全量采集。
- 每日增量采集。
- 手动指定日期范围采集。
- 历史行情重新采集。

系统不长期保存原始 K 线文件。

K 线在任务执行期间加载到内存，完成特征计算后释放。

### 4.9 前复权历史修正

前复权历史数据可能因为分红、拆分等因素发生变化。

当历史 K 线重新采集后，需要比较新旧数据。

如果历史行情发生变化：

1. 识别最早发生变化的交易日期。
2. 确定受影响 ETF。
3. 从最早变化日期开始重新计算相关特征。
4. 重算后续受影响的排名。
5. 重算相关日期的市场统计。
6. 保存修正后的每日结果。
7. 保留旧版本备份。

不能只重算最新交易日。

历史修正的完整执行规则见 `CALCULATION-ENGINE.md` 和 `ARCHITECTURE.md`。

## 5. 指数估值采集

### 5.1 采集目标

采集 ETF 所跟踪指数的估值数据。

支持：

- PE
- PB
- PS

估值数据以指数代码作为唯一关联对象。

ETF 通过 `trackIndex` 关联指数估值。

同一个指数对应的 ETF 共享估值数据。

### 5.2 数据源

当前已知估值接口：

```text
https://hongsehuojian.com/fundex-quote/index/valuation
```

已知请求参数：

| 参数          | 说明     |
| ------------- | -------- |
| securityCode  | 指数代码 |
| valuationType | 估值类型 |
| timeInterval  | 时间区间 |
| ts            | 时间戳   |

已知请求示例：

```ts
async function fetchIndexValuation(
  securityCode: string,
  valuationType: ValuationType,
) {
  const ret = await fetch(
    `https://hongsehuojian.com/fundex-quote/index/valuation?securityCode=${securityCode}&valuationType=${valuationType}&timeInterval=last_5_years&ts=${Date.now()}`,
    {
      headers: {
        accept: "application/json, text/plain, */*",
      },
    },
  );

  return ret.json();
}
```

说明：

- `securityCode` 使用指数代码。
- `valuationType` 分别获取 PE、PB、PS。
- `timeInterval` 当前使用 `last_5_years`。
- `ts` 使用当前请求时间戳。

具体 `valuationType` 的枚举值、响应结构和字段含义，必须以实际接口响应为准。

不得自行猜测 PE、PB、PS 的枚举值。

### 5.3 采集范围

每次估值采集任务：

1. 从当前 ETF 研究池提取所有唯一 `trackIndex`。
2. 去除重复指数代码。
3. 对每个指数分别请求 PE。
4. 对每个指数分别请求 PB。
5. 对每个指数分别请求 PS。
6. 解析并标准化返回数据。
7. 更新指数估值历史。

每个指数需要独立处理三个估值类型。

一个指数的 PE 采集失败，不得阻止该指数 PB 和 PS 的采集。

### 5.4 标准估值结构

系统内部统一使用：

```ts
type ValuationType = "PE" | "PB" | "PS";

interface IndexValuation {
  code: string;
  date: number; // YYYYMMDD
  type: ValuationType;
  value: number | null;
  historicalPercentile: number | null;
}
```

字段说明：

| 字段                 | 说明                 |
| -------------------- | -------------------- |
| code                 | 指数代码             |
| date                 | 估值实际日期         |
| type                 | PE、PB 或 PS         |
| value                | 当前估值数值         |
| historicalPercentile | 上游近五年历史百分位 |

### 5.5 百分位转换

上游 `historicalPercentile` 使用百分数形式时，统一转换为 0～1 的小数。

例如：

| 上游数值 | 保存值 |
| -------- | ------ |
| 73.76    | 0.7376 |
| 50       | 0.5    |
| 0        | 0      |
| 100      | 1      |

必须先确认上游字段的实际含义和范围。

不能因为字段名包含 percentile 就直接假设其一定是 0～100。

缺失值保存为 null，不得填充为 0。

### 5.6 PEG

如果上游返回 PEG：

- 可以作为扩展字段采集。
- 允许为 null。
- 当前不默认参与低估排名。
- 不允许在没有明确业务定义时自行计算 PEG。

### 5.7 估值日期

估值日期以数据源实际返回日期为准。

不能直接使用请求日期代替估值日期。

例如：

- 请求日期为 20261115。
- 上游最新估值日期为 20261113。

保存的日期必须是 20261113。

需要保留估值数据实际日期，以便计算与行情日期之间的滞后天数。

### 5.8 禁止未来数据

计算某个分析日期的 ETF 估值特征时：

- 只能使用估值日期小于或等于分析日期的数据。
- 不得使用晚于分析日期的估值数据。
- 如果找不到可用估值，返回 null。
- 不允许使用未来估值向历史日期回填。

### 5.9 估值历史保存

估值历史长期保存。

建议按指数代码拆分文件：

```text
data/
└── valuation/
    ├── 000001.json
    ├── 000016.json
    └── 000300.json
```

同一个指数文件保存 PE、PB、PS 的历史记录。

更新规则：

- 使用 `[code, date, type]` 作为唯一业务键。
- 已存在记录执行 Upsert。
- 新记录插入。
- 已存在记录更新。
- 上游某次没有返回某条历史记录时，不删除本地历史。
- 采集失败不覆盖原有有效数据。

## 6. 估值和行情采集频率

### 6.1 ETF 基础信息

每日研究池更新时采集。

### 6.2 ETF 日 K

每日行情采集任务执行。

正常情况下，收盘后获取最新完整日 K。

如果当天尚未收盘，不应将盘中行情当作最终日 K。

### 6.3 指数估值

估值任务每次执行时重新获取近五年数据。

是否执行由以下条件决定：

- 定时任务调度。
- 数据更新需求。
- 数据修正需求。
- 用户手动触发。

不要求每次前端页面打开时重新采集。

## 7. 采集任务管理

### 7.1 任务类型

```ts
type DataTaskType = "etf-basic" | "etf-kline" | "index-valuation";
```

### 7.2 任务状态

```ts
type DataTaskStatus =
  | "pending"
  | "running"
  | "success"
  | "partial_success"
  | "failed";
```

### 7.3 任务执行结果

```ts
interface DataTaskResult {
  taskType: DataTaskType;
  status: DataTaskStatus;
  startTime: string;
  endTime: string;
  successCount: number;
  failureCount: number;
  skippedCount: number;
  errors: Array<{
    code: string;
    message: string;
  }>;
}
```

### 7.4 部分成功

估值采集和 K 线采集均允许部分成功。

例如：

- 23 只 ETF 中 22 只采集成功。
- 1 只 ETF 采集失败。

此时任务状态为 `partial_success`。

不得因为单个 ETF 失败而丢弃其他 ETF 的有效数据。

但是，如果关键数据缺失导致无法生成可信的每日结果，必须明确标记本次分析结果不完整，不能伪装成完整成功。

### 7.5 请求失败重试

请求失败需要支持有限次数重试。

建议：

- 默认最多重试 3 次。
- 使用递增等待时间。
- 超时和临时网络错误允许重试。
- 参数错误、数据格式错误不应无限重试。
- 重试耗尽后记录失败。

具体超时时间和等待时间由系统配置管理。

### 7.6 请求频率

必须避免短时间大量请求导致上游接口限流。

要求：

- 支持请求间隔配置。
- 支持并发数量限制。
- 不允许无限并发。
- 对 HTTP 429 和服务端错误进行特殊处理。
- 请求失败时保留错误上下文。

## 8. 数据质量检查

### 8.1 基础信息检查

- ETF 代码不能为空。
- ETF 名称不能为空。
- 指数代码必须满足预期格式。
- 数值字段必须可以解析。
- 同一 ETF 不应重复出现。

### 8.2 K 线检查

- 日期合法。
- OHLC 数值有效。
- 最高价不小于最低价。
- 成交量和成交额不为负数。
- 同一代码和日期不能重复。
- 日期顺序正确。
- 检查异常的大幅价格变化。

### 8.3 估值检查

- 指数代码不能为空。
- 估值类型必须是 PE、PB 或 PS。
- 日期合法。
- 数值字段有效。
- 百分位范围符合上游定义。
- 同一指数、日期和类型不能重复。
- 不得出现未来日期数据。

### 8.4 缺失数据原则

所有缺失数据统一使用 null。

不允许：

- 用 0 代替缺失值。
- 用上一交易日价格随意填充缺失 K 线。
- 用未来估值填充历史日期。
- 将接口失败当成正常的空数据。

需要区分：

1. 上游确实没有数据。
2. 请求失败。
3. 响应格式异常。
4. 数据解析失败。

## 9. 数据修正与历史重采集

### 9.1 K 线修正

K 线发生历史变化时：

1. 比较新旧数据。
2. 找到最早变化日期。
3. 确定受影响 ETF。
4. 通知计算引擎。
5. 重算相关历史特征。
6. 重算相关历史排名。
7. 重算市场统计。
8. 备份旧结果。
9. 写入新结果。

### 9.2 估值修正

估值发生变化时：

1. 比较新旧估值。
2. 找到发生变化的指数、日期和类型。
3. 确定关联 ETF。
4. 重算对应估值特征。
5. 重算估值排名。
6. 重算市场估值统计。
7. 保存修正后的历史结果。

估值修正不影响：

- 收益计算。
- 趋势计算。
- 价格波动计算。
- 价格回撤计算。
- 成交活跃度计算。

### 9.3 历史保护

历史修正必须保留旧版本备份。

不能因为一次接口采集失败而清空历史数据。

## 10. 配置管理

数据源相关参数统一配置。

建议配置：

```ts
interface DataSourceConfig {
  timeout: number;
  retryCount: number;
  retryDelay: number;
  concurrency: number;
  requestInterval: number;
}
```

要求：

- 请求参数集中管理。
- 数据源地址集中管理。
- 不在业务代码中散落 URL。
- 不在多个模块中重复实现字段转换。
- 不将密钥或敏感凭证写入公开静态文件。
- 不将采集配置与前端展示配置混合。

如果数据源需要认证信息，使用本地环境变量配置。

## 11. 未验证接口的处理规范

以下内容必须在首次接入时进行实测。

### 11.1 ETF 基础信息

待验证：

- 当前使用的数据源完整 URL。
- 请求参数。
- 分页方式。
- 原始响应结构。
- scale 单位。
- amount 单位。
- premiumRate 单位。

### 11.2 ETF 日 K

待验证：

- 当前 AkShare 版本。
- `fund_etf_hist_em` 的实际返回字段。
- `qfq` 是否正确返回前复权行情。
- 成交量单位。
- 成交额单位。
- 涨跌幅单位。
- 不同 ETF 市场的兼容性。

### 11.3 指数估值

- PE、PB、PS 对应的 `valuationType` 枚举值。
- 完整响应结构。
- 历史记录字段。
- 日期字段格式。
- value 字段含义。
- historicalPercentile 字段含义。
- 百分位取值范围。
- 缺失值表现。
- 指数代码是否可以直接作为 securityCode。

### 11.4 接口验证要求

首次实现时，必须先完成接口验证。

验证结果至少包含：

- 请求地址。
- 请求参数。
- 响应示例。
- 字段说明。
- 单位说明。
- 异常响应示例。
- 标准化结果。

通过验证后，将实际接口结构补充到数据源适配器和相关测试中。

不允许 Codex 为了让程序运行而编造模拟接口响应并将其当作真实数据。

## 12. 验收标准

### 12.1 ETF 基础信息

- 能够获取 ETF 基础信息。
- 能够解析原始响应。
- 能够转换成标准数据结构。
- 能够正确处理 null。
- 能够正确处理数值 0。
- 能够识别异常字段。
- 能够输出采集结果。

### 12.2 ETF 日 K

- 能够获取前复权日 K。
- 能够转换为统一 Kline 结构。
- 能够正确处理日期。
- 能够正确处理 OHLC。
- 能够正确处理成交量和成交额。
- 能够校验异常行情。
- 能够支持历史和增量采集。
- 不长期保存原始 K 线。

### 12.3 指数估值

- 能够按指数代码采集。
- 能够分别采集 PE、PB、PS。
- 能够转换为统一结构。
- 能够将历史百分位转换为 0～1。
- 能够长期保存估值历史。
- 能够执行 Upsert。
- 能够处理部分失败。
- 不会删除上游缺失的历史记录。
- 不使用未来估值数据。

### 12.4 任务能力

- 能够手动执行采集。
- 能够定时执行采集。
- 能够记录执行日志。
- 能够有限重试。
- 能够输出部分成功状态。
- 能够进行历史数据修正。
- 采集失败时不会破坏已有有效数据。
